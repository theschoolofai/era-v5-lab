# Every code, cause and reason, with what to do

Generated by `python metrics/explain.py --all` from `common/reasons.py` and `metrics/catalog.yaml`.

## Job exit codes

| Code | Means | Already done | You do |
|---|---|---|---|
| 0 DONE | Training finished and the final checkpoint is committed. | Slurm marks the job COMPLETED. | nothing |
| 75 RETRY | The job stopped in a safe state (it just saved, or there was nothing to save) and asks to run again. Also used for one-off crashes. | Slurm requeues the job (RequeueExit=75); it restarts from latest.json, on another node if needed. | nothing, unless it repeats: then see Q-05 (interruptions) and the cause in the job comment |
| 78 HELD | The job stopped and must NOT be retried: retrying would burn GPU hours for nothing (NaN, loss spike, failed restore checks, changed environment, or a crash loop). | Slurm holds the job (RequeueExitHold=78; squeue shows SPECIAL_EXIT / JobHeldUser). Nothing bad was saved. | read the cause in the job comment (scontrol show job <id> | grep Comment) and follow its entry here; then `scontrol release <id>` or submit the fix |

Raw trainer exit codes (before the wrapper maps them to 75, or 78 after 3 crashes in 30 min):

- `1`: Python error (an uncaught exception, often a NCCL error raised by TORCH_NCCL_ASYNC_ERROR_HANDLING)
- `124`: a command timed out
- `134`: abort (SIGABRT), often NCCL or CUDA aborting the process
- `137`: killed with SIGKILL: out of memory (kernel OOM killer), kill -9, or Slurm after KillWait
- `139`: segmentation fault (SIGSEGV): a crash in native code (CUDA, NCCL, a custom kernel)
- `143`: SIGTERM not handled by the trainer

## Causes (the `cause` field in events, and the Slurm job comment)

| Cause | Severity | Means | Already done | You do | Alert |
|---|---|---|---|---|---|
| `done` | none | Training reached its last step. | final checkpoint committed | nothing |  |
| `saved_and_stopped` | none | A stop signal arrived (preemption, spot notice, health drain or an operator), the job saved, and stopped. | emergency checkpoint committed; Slurm requeues the job, it restarts from that checkpoint (≈0 work lost) | nothing |  |
| `hang_watchdog` | medium | No training step finished within WATCHDOG_S: a frozen rank, a deadlock or a data wait. | all Python stacks dumped to the job log; exit 75; Slurm restarts from the last checkpoint | read the stack dump in the job log (which rank, which call). Two in an hour pages (H-14) | H-14 |
| `crash` | low | The trainer died without saying why (see trainer_exit: 1 Python error, 137 killed/OOM, 139 segfault). | the wrapper turned it into 75: Slurm restarts from the last checkpoint; work since that commit is lost | nothing for one crash; look at the job log if it repeats (3 in 30 min holds the job) |  |
| `crash_loop` | high | The job crashed 3 times within 30 minutes. It is not a one-off fault. | job held so it stops burning GPU hours | read the last job log for the real error, fix it, then `scontrol release <id>` | Q-04 |
| `unknown_fatal` | high | The trainer exited 78 but left no exit note (a trainer that does not call write_exit_note). | job held | read the end of the job log for the FATAL line; then follow that cause here | Q-02 |
| `nonfinite` | high | The loss (or the state) became NaN/Inf. Nothing was saved after it. | no checkpoint written; job held | roll back: sbatch --export=ALL,TRAIN_EXTRA="--from-step <last good step> --skip <N> --branch <new name>" slurm/mainrun.sbatch (last good step: python ckpt/ckpt.py list --run <run>), skipping the batches around the bad step | CK-07 |
| `loss_spike` | high | The loss stayed above 1.5 × its recent median for 3 steps: the model is diverging, even without NaN. | no checkpoint written during the spike; job held | roll back: sbatch --export=ALL,TRAIN_EXTRA="--from-step <last good step> --skip <N> --branch <new name>" slurm/mainrun.sbatch (last good step: python ckpt/ckpt.py list --run <run>); tell Team 05 | H-24 |
| `StrictLoadError` | high | The model code has different tensor names, shapes or dtypes than the checkpoint (the V4 misload). | restore refused; every key that differs is listed in the job log | fix the model code or the checkpoint mapping; never resume by ignoring keys | CK-06 |
| `FrozenChangedError` | high | A tensor that must never train (e.g. the KE2 Kronecker tables) changed since the last checkpoint. Training touched it: a missing requires_grad=False, or an optimizer that includes it. | nothing saved (the previous checkpoint is still good); job held | find which code trains the named tensor (the job log lists it), fix it, then roll back to the last checkpoint: roll back: sbatch --export=ALL,TRAIN_EXTRA="--from-step <last good step> --skip <N> --branch <new name>" slurm/mainrun.sbatch (last good step: python ckpt/ckpt.py list --run <run>) | CK-06 |
| `DataManifestError` | high | The data loader's shard list differs from the one this checkpoint was trained on. Resuming would continue on other data without anyone noticing. | restore refused before any step; nothing was lost | point the loader back at the run's shard list, or, if new data is intended, start a new branch and tell Teams 01/02 | CK-06 |
| `EnvMismatchError` | high | The software or config differs from the checkpoint (image digest, torch/CUDA/NCCL, config sha, OMP_NUM_THREADS). | restore refused; the differences are listed in the job log | if the change is intended and approved, resubmit with TRAIN_EXTRA=--allow-env-change (it is logged); otherwise go back to the old image | CK-06 |
| `CheckpointError` | high | Every committed checkpoint failed its checks, or the requested step does not exist. | restore refused | python ckpt/ckpt.py list/verify --run <run>; check S3 and CK-04/CK-05 | CK-06 |
| `nvme_full` | high | The node's NVMe has less free space than 1.2 × this node's checkpoint share. | save skipped (training continues, but nothing new is protected) | free NVMe space (old restore folders, data cache) or drain the node | CK-03 |
| `IntegrityError` | high | A checkpoint file does not match its sha256: damaged on disk, network or S3. | the damaged checkpoint is never used; a restore falls back to the previous commit | pin the last good checkpoint (ckpt.py pin); find the hop that corrupts data | CK-04 |
| `RestoreCheckError` | high | The restored state is not the saved state (digest, probe loss, next batch or frozen hashes differ). | the job fell back to the previous commit | compare the two printed values in the job log; do not continue on that checkpoint | CK-05 |
| `UploadTimeout` | medium | A rank did not finish its S3 upload in time. | save not committed; training continues | check S3 errors and upload throughput (CK-11) | CK-03 |
| `FencedError` | medium | A newer attempt of this run claimed latest.json (a higher epoch), so this attempt may not commit. Two attempts were alive at once: usually a node that lost its network, so Slurm started a new job while the old one kept running. | this attempt's commit was refused and it stopped; the pointer and the newer attempt are untouched | nothing for the run; find out why the old attempt was still alive (node network, slurmd) and drain that node if it repeats |  |
| `ReshardError` | high | The checkpoint was saved by a data loader that keeps a separate position per rank. At another world size those positions do not map to the new ranks, so data would repeat or be skipped. | restore refused before any step; nothing was lost | resubmit at the saved world size (the job log names it), or fix the loader to keep one global ledger offset (ckpt/loader_contract.py) | CK-06 |
| `crash_ledger_unavailable` | medium | The crash was retried, but the crash count could not be written to the run's S3 folder, so the 3-in-30-min crash-loop cap is not counting. | job requeued as a normal crash | check S3 access from the batch node (the same fault usually also fails checkpoint uploads) | CK-03 |

## Node drain reasons (`sinfo -R` shows `v5:<names>`)

| Reason | Means | Already done | You do |
|---|---|---|---|
| `spot_notice` | the cloud will reclaim this spot instance in 2 minutes. | node drained, jobs saved and moved to the spare | nothing; the instance goes away by itself |
| `gpu_inventory` | Fewer GPUs visible than expected, or nvidia-smi could not run (driver broken or GPU hung). | node drained, jobs saved and moved | reboot the instance; if still wrong, replace it |
| `ecc_uncorrectable` | A GPU memory error lost data. | node drained, jobs saved and moved | replace the instance (stop/start moves it to new hardware) |
| `remapped_rows` | GPU memory row remap failed (or is pending a reset). | node drained on failure | failure: replace; pending: reset the GPU / reboot |
| `xid` | The GPU driver logged a fatal Xid error (79 off the bus, 95 uncontained memory error, …), or Xid 94 (contained ECC) twice on one GPU within 24 h. | node drained, jobs saved and moved | replace the instance; the Xid code is in the health report |
| `dcgm_diag` | NVIDIA's diagnostic failed. | node drained | replace the instance |
| `dcgm_health` | DCGM's background health watch reports a GPU failure (PCIe, memory, NVLink, thermal or power). | node drained; its jobs saved and moved | run `health_check.py --mode full`; replace if it fails again |
| `gpu_temperature` | A GPU is at its slowdown temperature. | node drained | check cooling; replace if repeated |
| `nvme_free` | Local disk too full for the next checkpoint. | node drained | clean /nvme, then `scontrol update nodename=<n> state=resume` |
| `clock_offset` | The node clock is off by more than 100 ms. | node drained | fix chrony (the cloud's time service), then resume the node |
| `nccl_collectives` | The collective test did not finish (hang, crash or timeout). | node drained | run health_check.py --mode full on it; read the NCCL flight-recorder dump; replace if it fails again |
| `nccl_all_reduce` | All-reduce (data-parallel gradients) gave a wrong value or was too slow. | node drained | run health_check.py --mode full on it; replace if it fails again |
| `nccl_reduce_scatter` | Reduce-scatter (ZeRO/FSDP gradients) gave a wrong value or was too slow. | node drained | run health_check.py --mode full on it; replace if it fails again |
| `nccl_all_gather` | All-gather (ZeRO-3/FSDP weights) gave a wrong value or was too slow. | node drained | run health_check.py --mode full on it; replace if it fails again |
| `nccl_all_to_all` | All-to-all (MoE expert exchange) gave a wrong value or was too slow. | node drained | run health_check.py --mode full on it; replace if it fails again |
| `nvlink` | An NVLink link between GPUs is inactive: no error, but all-reduce runs at about half speed. | node drained | reset the GPUs or reboot; replace the instance if the link stays down |
| `drill_force_fail` | A drill forced this node to fail (test only). | node drained | remove /var/lib/v5-health/force_fail and resume the node |

After the fix: `scontrol update nodename=<node> state=resume`.

## Slurm states and pending reasons

| Shown | Means |
|---|---|
| `SPECIAL_EXIT` | held after exit 78 (RequeueExitHold). Read the job Comment for the cause. |
| `JobHeldUser` | held after exit 78, or by `scontrol hold`. Read the job Comment for the cause. |
| `BeginTime` | requeued; Slurm waits for the old launch credential to expire (≈ 50 s). Normal after a restart. |
| `Resources` | waiting for free nodes. For the main run: Q-01 pages after 10 min (not enough healthy nodes). |
| `Priority` | higher-priority jobs are ahead. Normal for team jobs. |
| `AssocGrpCPUMinutesLimit` | the account's budget (GrpTRESMins) is used up. Talk to the lead (Q-15). |
| `AssocGrpGRESMinutes` | the account's GPU-minute budget is used up. Talk to the lead (Q-15). |
| `AssocGrpGRES` | the team already uses its GPU share (GrpTRES=gres/gpu). It starts when its own jobs free GPUs. |
| `QOSMaxGRESPerJob` | the job asks for more GPUs than its QOS allows per job. Ask for fewer, or use another QOS. |
| `QOSMaxWallDurationPerJobLimit` | --time is above the QOS MaxWall. Ask for less; long runs requeue themselves. |
| `QOSMaxSubmitJobPerUserLimit` | the user has the most jobs this QOS lets one user queue. Wait or cancel some. |
| `QOSMaxJobsPerUserLimit` | the user already runs the most jobs this QOS allows at once. It starts when one ends. |
| `AssocGrpNodeLimit` | the team already holds its 2 nodes (GrpTRES=node=2). It starts when one frees up. |
| `ReqNodeNotAvail` | the nodes asked for are drained or down. Check `sinfo -R`. |
| `PREEMPTED` | a team job gave its node to the main run; it saved and is back in the queue. |
| `NODE_FAIL` | the node stopped answering (SlurmdTimeout 30 s); the job is requeued by Slurm. |
| `REQUEUED` | the job is back in the queue and restarts from its last checkpoint. |
