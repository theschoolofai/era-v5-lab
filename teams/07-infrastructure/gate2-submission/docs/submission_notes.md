  supervisor, job-package admission, Slurm adapter and validations.

  workflow had an incorrect root build context and a personal registry target.
- The external Docker Slurm demo Compose checkout and the real H100 model,
  configuration and training data. Neither belongs to this source folder.

## After extraction

1. Copy the contents of `teams/07-infrastructure/` into the corresponding
   folder in the shared repository; review the diff before committing.
2. From that folder create a Python virtual environment, install requirements,
   validate the example job and run host CPU tests (see `docs/runbook.md`).
3. To rerun Slurm tests, first provision an authorized two-node CPU demo with
   Slurm, matching Unix users, shared `/data` and Python; inspect node health.
4. Commit only Team 7's intended source, docs, tests and curated evidence.
5. If the shared-repo owners want CI/Docker publishing, create a separately
   reviewed *root-level* workflow with the team-scoped Docker context.

## Public-repository caution

The retained **historical raw execution logs** may contain original workstation
usernames and absolute paths. They are preserved as test records, not runnable
commands. Review this metadata before committing to a public repository if
local identity/path disclosure is a concern. There are no bundled credentials
or access tokens intentionally included.

## Honest scope

Historical CPU restore/restart comparison PASS (steps 101–200, SIGKILL
after 125, restart from COMPLETE 100). Two-user CPU Slurm queue PASS.
No H100/CUDA, actual MoE trainer, or automatic whole-node/Slurm-allocation
recovery has been validated. This archive is **not** the distinct single-GPU
G7 SIGKILL restart-test job; those sources and config are not included.

`docs/week1/source_sha256.json` is a *historical input inventory*, not a list
of files currently present. The curated checksum file is under `evidence/`.
